# P4: priority, SLA, escalation, notifications, analytics

Read [foundation.md](foundation.md) and the [integration guide](integration-guide.md) first. This is the design P4 is
building against. Nothing here is implemented yet unless the roadmap at the end says so. Sections marked **Proposed** are
decisions that other people's code depends on; please comment on the PR if you disagree.

| Area | Backend package (`com.itsm.*`) | Migration | Depends on |
|---|---|---|---|
| Priority | `priority/` | none | P1 `ServiceCatalog` |
| SLA tracking | `sla/` | `V40` | P1 `SlaPolicyProvider`, the `incidents` table (P2/P3) |
| Escalation | `escalation/` | `V41` | SLA, P1 `UserDirectory`, P3 `TechnicianWorkloadProvider` |
| Notifications | `notification/` | `V42` | SLA, escalation, P2/P3 domain events |
| Analytics | `analytics/` | `V43` (indexes or views, only if needed) | everything above, P3 `incident_feedback` |

All P4 modules follow the one rule: they import `com.itsm.common.*` and nothing from another module's package.

## 1. Priority

Priority is computed **once, when an incident is classified**, from what the reporter says and what the service catalog
knows. It is a pure function, so the same inputs always give the same priority and every result can be explained.

### Inputs

| Input | Values | Source |
|---|---|---|
| Impact: how many people are affected | `HIGH` (organisation-wide or many users), `MEDIUM` (a department or team), `LOW` (one person) | reporter, confirmed by P2 at classification |
| Urgency: how soon it hurts | `HIGH` (work has stopped, no workaround), `MEDIUM` (degraded, a workaround exists), `LOW` (an inconvenience) | reporter, confirmed by P2 |
| Business criticality of the service | 1 (low) to 5 (mission critical) | P1 `ServiceCatalog.findById(id).businessCriticality` |
| Dependent services | number of services that depend on this one, directly or transitively | P1 `ServiceCatalog.dependentsOf(id)`, walked transitively |

`Impact` and `Urgency` are shared vocabulary (P2 stores them, P4 reads them), so they live in `common/model` next to
`Priority`.

### Algorithm

1. **Effective impact.** If **3 or more active services** depend on the incident's service (transitively), raise impact by one
   level, at most `HIGH`. An outage of a shared service spreads.
2. **Base priority** from the ITIL impact × urgency matrix, using the effective impact:

   | Impact \ Urgency | HIGH | MEDIUM | LOW |
   |---|---|---|---|
   | **HIGH** | P1 | P2 | P3 |
   | **MEDIUM** | P2 | P3 | P4 |
   | **LOW** | P3 | P4 | P4 |

3. **Criticality adjustment**, at most one level, never past `P1` or `P4`:
   * criticality **5** (mission critical): one level more urgent;
   * criticality **1** (low): one level less urgent;
   * 2 to 4: no change.

The result carries the base priority and a list of plain-language reasons (for the audit trail and the UI), for example
`Impact raised from MEDIUM to HIGH: 4 services depend on Campus Wi-Fi` and `Raised one level: service criticality is 5`.

Worked examples:

| Impact | Urgency | Criticality | Dependents | Result |
|---|---|---|---|---|
| HIGH | HIGH | 3 | 0 | P1 |
| MEDIUM | HIGH | 5 | 0 | P2 → **P1** |
| MEDIUM | MEDIUM | 3 | 4 | impact → HIGH, **P2** |
| HIGH | HIGH | 1 | 0 | P1 → **P2** |
| LOW | LOW | 5 | 0 | P4 → **P3** |

The thresholds (3 dependents, criticality 5 and 1) are **tunable constants, not from the spec**. They are in one place in
`priority/` and covered by tests at every boundary.

### Contract (Proposed)

P4 provides a new SPI in `common/spi`, implemented only by P4:

```kotlin
interface PriorityPolicy {
    /** @throws ServiceNotFound if [serviceId] is unknown. An inactive service is still assessed. */
    fun assess(serviceId: Long, impact: Impact, urgency: Urgency): PriorityAssessment
}
```

* **P2** calls it when classifying an incident and stores the returned `priority` (plus `impact` and `urgency`, so a
  later recalculation has its inputs). P2 publishes `INCIDENT_CLASSIFIED`; the assessment's reasons go in its metadata.
* `ServiceNotFound` is an answer, not a failure: it does not mark the caller's transaction rollback-only.
* **Later priority changes** (an admin override, or a recalculation after the reporter changes impact or urgency) publish
  `INCIDENT_PRIORITY_CHANGED` and make P4 recalculate the SLA deadlines. Who writes `incidents.priority` for an override is
  an open question (section 8).

## 2. SLA tracking

### What is measured (Proposed)

| Clock | Starts | Stops (met) | Target |
|---|---|---|---|
| **Response** | `created_at` | `first_response_at` (the first `ACKNOWLEDGE`, never cleared) | `SlaPolicyView.responseTarget` |
| **Resolution** | `created_at` | `resolved_at` | `SlaPolicyView.resolutionTarget` |

* Clocks run from when the incident was **reported**, not from classification: that is what the reporter experiences.
  The policy (and so the deadline) is only known once the incident is `CLASSIFIED` with a service and priority, so P4
  creates the SLA record then and back-dates the deadlines to `created_at`.
* **24×7 calendar.** No business hours or holidays (out of scope for the course project; noted as a later extension).
* **Warning** when `warningThresholdPct` (default 80) of a target has elapsed and the clock has not stopped.
* **Breach** when the deadline passes and the clock has not stopped. A breach is recorded once and never removed, even if
  the clock later stops or a recalculation would move the deadline.

### Pauses and changes (Proposed, answers P3's question)

| Event | Response clock | Resolution clock |
|---|---|---|
| `REQUEST_INFO` → `PENDING_INFO` | not affected (already met: the incident was acknowledged) | **paused** while waiting on the reporter |
| `PROVIDE_INFO` → `IN_PROGRESS` | n/a | resumes; the deadline moves later by the paused time |
| `RESOLVE` | n/a | stops (met or breached) |
| `REOPEN` | stays met | **resumes**; the time spent in `RESOLVED` counts as paused (the reporter had been told it was fixed) |
| `REASSIGN` | no change (`first_response_at` is never cleared) | no change |
| Priority changed | deadline recalculated from `created_at` with the new target | same |
| `VERIFY`, `CLOSE` | no change | no change |

### When no policy applies (answers P1's question)

* `SlaPolicyProvider.resolve` answering **422 `MISSING_SLA_CONFIG`**: P4 records the SLA as `NO_POLICY`, publishes
  `SLA_POLICY_MISSING` once, notifies admins, and retries on every monitor run until a policy exists. The incident flow is
  never blocked. P4 does not invent a duration.
* **Inactive service still resolves**: agreed, historical incidents keep their targets.
* **`ServiceNotFound`**: treated like `NO_POLICY` with a different reason (it should not happen once P2 adds the foreign key).
* **Cross-priority consistency** (P1 targets never looser than P2): P4 does not need the backend to enforce it. Each
  incident uses the policy for its own priority. Keeping it a UI rule is fine.

### Storage (`V40`)

`incident_sla`, one row per incident:

| Column | Notes |
|---|---|
| `incident_id` | PK, FK `incidents (id)` |
| `policy_id`, `policy_scope` | which policy supplied the targets (`SERVICE` or `GLOBAL`), null with `NO_POLICY` |
| `priority` | the priority the deadlines were computed for |
| `response_due_at`, `resolution_due_at` | current deadlines, including pauses |
| `response_warning_at`, `resolution_warning_at` | when the warning fires |
| `response_status`, `resolution_status` | `RUNNING`, `PAUSED`, `WARNING`, `MET`, `BREACHED`, `NO_POLICY` |
| `paused_since`, `paused_total_seconds` | resolution pause bookkeeping |
| `response_breached_at`, `resolution_breached_at` | set once, never cleared |
| `version`, `created_at`, `updated_at` | optimistic lock and timestamps |

### Monitor

`SlaMonitor` is a scheduled job (every 60 s, configurable) annotated `@Transactional`, auditing as
`AuditActor.system("SLA_MONITOR")`. Each run:

1. creates SLA records for classified incidents that have none (and retries `NO_POLICY` ones);
2. applies state changes (pause, resume, met) since the last run;
3. raises warnings and breaches whose time has come, each exactly once.

Audit actions: `SLA_STARTED`, `SLA_WARNING_RAISED`, `SLA_BREACHED`, `SLA_MET`, `SLA_PAUSED`, `SLA_RESUMED`,
`SLA_RECALCULATED`, `SLA_POLICY_MISSING` (entity type `INCIDENT_SLA`, entity id = incident id). Warnings and breaches also
raise P4 domain events (`SlaWarningRaised`, `SlaBreached`) that escalation and notifications react to.

The application needs `@EnableScheduling` (it has only `@EnableAsync` today). P4 adds it in its own configuration class,
so `ItSmApplication` is not touched.

**Until P2/P3 publish domain events** (section 6) the monitor polls the `incidents` table read-only, through one adapter
class (`sla/IncidentSnapshotReader`) that is the only P4 code aware of that table. Pause times are then accurate to the
polling interval. When the events exist, the adapter is replaced and the rest of the module is unchanged.

## 3. Escalation

### Path

Technician (assignee) → `UserDirectory.escalationChain(assignee)` in order (nearest team lead first) →
`UserDirectory.listAdmins()` (system admin and IT manager are both `ADMIN`).

### Triggers (Proposed)

| Trigger | Escalates to |
|---|---|
| Response or resolution **warning** | nobody: the assignee is notified (section 4) |
| **Response breach** | first level of the chain (the team lead) |
| **Resolution breach** | first level of the chain |
| Resolution still open at **150 %** of the target | next level of the chain |
| Resolution still open at **200 %** of the target | admins |
| **Unassigned** (`CLASSIFIED`) longer than `unassignedEscalationMinutes` | admins (there is no assignee, so no chain) |
| P3 reports `NO_ELIGIBLE_TECHNICIAN` | admins, immediately |

* An incident escalates to each level **at most once** per clock. A reassignment does not reset levels already reached.
* An empty chain (a technician without a team lead) skips straight to admins. An inactive manager is already skipped by P1.
* Escalation does **not** reassign the incident; it notifies and records. Reassigning stays a human decision through P3.
* `INCIDENT_ESCALATED` audit event, metadata: level, trigger, target user ids.
* `TechnicianWorkloadProvider` is used to flag **SLA risk early**: an incident whose assignee is at or above their
  `maxWorkload` and past 50 % of the resolution target is marked at risk (a notification, not an escalation).

### Settings (answers P1's open question 3)

**P4 owns `unassignedEscalationMinutes`** (default 30). It lives in P4's own `escalation_settings` singleton (`V41`), with
the 150 % and 200 % thresholds, behind `GET/PUT /api/admin/escalation-settings` (`SLA_CONFIGURE`). That route needs one
`SecurityConfig` line from P1, requested in the PR that adds it.

### Storage (`V41`)

`incident_escalations` (append-only: incident, level, trigger, target user ids, created at) and `escalation_settings`.

## 4. Notifications

* **Channels** are an interface; a new channel is a new class:

  ```kotlin
  interface NotificationChannel { val key: String; fun deliver(notification: Notification) }
  ```

  `IN_APP` (stored, shown in the app), `EMAIL` and `SMS` (**simulated**: they log what would be sent, as `PRODUCT.md`
  says).
* **Channel by severity:** P1 → in-app + email + SMS; P2 → in-app + email; P3 and P4 → in-app only.
* **Triggers** are domain events, never audit events. Notifications are sent `AFTER_COMMIT`, so a rolled-back change
  notifies nobody, and a failed email never undoes the change.

| Event | Who is notified |
|---|---|
| Incident classified (priority known) | reporter |
| Assigned / reassigned | the new assignee; the reporter |
| Info requested | reporter |
| Resolved | reporter (please verify) |
| Reopened | assignee |
| SLA warning, SLA risk | assignee |
| SLA breach | assignee, plus whoever the escalation reached |
| Escalated | the escalation targets |
| No policy / no eligible technician | admins |

* **Storage (`V42`):** `notifications` (recipient, type, incident id, title, body, severity, created at, read at). Only
  `read_at` ever changes.
* **API:** `GET /api/notifications` (own only, paged), `GET /api/notifications/unread-count`,
  `POST /api/notifications/{id}/read`, `POST /api/notifications/read-all`. Authenticated users only; each user sees only
  their own.

## 5. Analytics

Read-only, `ANALYTICS_VIEW` (admins), under `/api/admin/analytics/*`, every query filtered by a date range:

* SLA compliance (met vs breached) by priority, service and category;
* mean and 90th-percentile time to respond and to resolve;
* breach and escalation counts over time;
* open incidents by state and priority, unassigned count;
* technician workload (from `TechnicianWorkloadProvider`) and average feedback rating (from P3's `incident_feedback`).

Plain aggregate SQL first. `V43` only if a query needs an index or a view.

## 6. Domain events P4 asks P2 and P3 to publish (Proposed)

Audit is a record, not a message bus, so P4 needs its own events. Proposed shape, in `common/event` (a P1-reviewed PR):

| Event | Published by | When | Fields |
|---|---|---|---|
| `IncidentClassified` | P2 | `CLASSIFY` committed | incidentId, serviceId, categoryId, priority, occurredAt |
| `IncidentStateChanged` | P3 | every transition | incidentId, from, to, transition, actorId, occurredAt |
| `IncidentAssigned` | P3 | assign and reassign | incidentId, assigneeId, previousAssigneeId, occurredAt |
| `IncidentAssignmentFailed` | P3 | outcome `NO_ELIGIBLE_TECHNICIAN` | incidentId, occurredAt |
| `IncidentPriorityChanged` | whoever writes the priority | override or recalculation | incidentId, from, to, actorId, occurredAt |

* Published with Spring's `ApplicationEventPublisher` **inside** the business transaction.
* P4's SLA listeners run `BEFORE_COMMIT` (the SLA row commits with the change); notification listeners run `AFTER_COMMIT`.
* Events are immutable data classes holding ids only, never entities or personal data.
