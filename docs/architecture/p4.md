## 1. Priority

Priority is computed **once, when an incident is reported**: P2's intake creates incidents directly in `CLASSIFIED`, so
reporting and classifying are the same step. It comes from what the reporter says and what the service catalog knows. It is a pure function, so the same inputs always give the same priority and every result can be explained.

### Inputs

| Input | Values | Source |
|---|---|---|
| Impact: how many people are affected | `HIGH` (organisation-wide or many users), `MEDIUM` (a department or team), `LOW` (one person) | the reporter, answering "How many people are affected?" on the report form |
| Urgency: how soon it hurts | `HIGH` (work has stopped, no workaround), `MEDIUM` (degraded, a workaround exists), `LOW` (an inconvenience) | the reporter, answering "Can you still work?" |
| Business criticality of the service | 1 (low) to 5 (mission critical) | P1 `ServiceCatalog.findById(id).businessCriticality` |
| Dependent services | number of **active** services that depend on this one, directly or transitively | P1 `ServiceCatalog.listActive()`: the reverse graph is built in memory, so one call covers the whole walk |

`Impact` and `Urgency` are shared vocabulary (P2 stores them, P4 reads them), so they live in `common/model` next to
`Priority`.

### Algorithm

1. **Effective impact.** If **3 or more active services** depend on the incident's service (transitively), raise impact by one
   level, at most `HIGH`. An outage of a shared service spreads.
2. **Base priority** from the ITIL impact × urgency matrix, using the effective impact:

   | Impact \ Urgency | HIGH | MEDIUM | LOW |
   |---|---|---|---|
   | **HIGH** | P1 | P2 | P3 |
   | **MEDIUM** | P2 | P3 | P4 |
   | **LOW** | P3 | P4 | P4 |

3. **Criticality adjustment**, at most one level, never past `P1` or `P4`:
   * criticality **5** (mission critical): one level more urgent;
   * criticality **1** (low): one level less urgent;
   * 2 to 4: no change.

The result carries the base priority and a list of plain-language reasons (for the audit trail and the UI), for example
`Impact raised from MEDIUM to HIGH: 4 services depend on Campus Wi-Fi` and `Raised from P2 to P1: Campus Wi-Fi has business
criticality 5`.

Worked examples:

| Impact | Urgency | Criticality | Dependents | Result |
|---|---|---|---|---|
| HIGH | HIGH | 3 | 0 | P1 |
| MEDIUM | HIGH | 5 | 0 | P2 → **P1** |
| MEDIUM | MEDIUM | 3 | 4 | impact → HIGH, **P2** |
| HIGH | HIGH | 1 | 0 | P1 → **P2** |
| LOW | LOW | 5 | 0 | P4 → **P3** |

The thresholds (3 dependents, criticality 5 and 1) are **tunable constants, not from the spec**. They are in one place
(`priority/PriorityCalculator`) and covered by tests at every boundary.

### Contract (implemented)

P4 provides an SPI in `common/spi`; `priority/CatalogPriorityPolicy` is the only implementation:

```kotlin
interface PriorityPolicy {
    /** @throws ServiceNotFound if [serviceId] is unknown. An inactive service is still assessed. */
    fun assess(serviceId: Long, impact: Impact, urgency: Urgency): PriorityAssessment
}
```

* **P2's intake** calls it for every new incident. `POST /api/incidents` takes `impact` and `urgency`, **never a
  priority**, so a reporter cannot choose P1. P2 stores the returned `priority` plus the answers (`incidents.impact` /
  `urgency`, `V22`) so a later recalculation has its inputs, and puts the reasons in `INCIDENT_CLASSIFIED` as
  `priorityReasons`. Full contract: the integration guide, "P2: incident intake".
* `ServiceNotFound` is an answer, not a failure: it does not mark the caller's transaction rollback-only.
* The mock frontend service copies the matrix only for offline demos; the live app always asks the backend.
* **Later priority changes** (an admin override, or a recalculation after the reporter changes impact or urgency) publish
  `INCIDENT_PRIORITY_CHANGED` and make P4 recalculate the SLA deadlines. Who writes `incidents.priority` for an override is
  an open question (section 8).

## 2. SLA tracking

Implemented in `sla/` (#15); the API is documented in the integration guide, "SLA tracking".

### What is measured

| Clock | Starts | Stops (met) | Target |
|---|---|---|---|
| **Response** | `created_at` | `first_response_at` (the first `ACKNOWLEDGE`, never cleared) | `SlaPolicyView.responseTarget` |
| **Resolution** | `created_at` | `resolved_at` | `SlaPolicyView.resolutionTarget` |

* Clocks run from when the incident was **reported** (`created_at`): that is what the reporter experiences. P4 creates the
  SLA record at the first monitor run after the incident appears (it is `CLASSIFIED` from the start), within one polling
  interval, and dates the deadlines from `created_at`.
* Targets are **copied** from the policy when tracking starts, so a later policy edit does not move existing deadlines.
* **24×7 calendar.** No business hours or holidays (out of scope for the course project; noted as a later extension).
* **Warning** when `warningThresholdPct` (default 80) of a target has elapsed and the clock has not stopped.
* **Breach** when the deadline passes and the clock has not stopped. A breach is recorded once and never removed, even if
  the clock later stops or a recalculation would move the deadline.

### Pauses and changes (answers P3's question)

| Event | Response clock | Resolution clock |
|---|---|---|
| `REQUEST_INFO` → `PENDING_INFO` | not affected (already met: the incident was acknowledged) | **paused** while waiting on the reporter |
| `PROVIDE_INFO` → `IN_PROGRESS` | n/a | resumes; the deadline moves later by the paused time |
| `RESOLVE` | n/a | stops (met or breached) |
| `REOPEN` | stays met | **resumes**; the time spent in `RESOLVED` counts as paused (the reporter had been told it was fixed) |
| `REASSIGN` | no change (`first_response_at` is never cleared) | no change |
| Priority changed (no path changes it after creation yet) | deadline recalculated from `created_at` with the new target | same |
| `VERIFY`, `CLOSE` | no change | no change |

### When no policy applies (answers P1's question)

* `SlaPolicyProvider.resolve` answering **422 `MISSING_SLA_CONFIG`**: P4 records the SLA as `NO_POLICY`, publishes
  `SLA_POLICY_MISSING` once, and retries on every monitor run until a policy exists (notifying admins comes with
  notifications, section 4). The incident flow is
  never blocked. P4 does not invent a duration.
* **Inactive service still resolves**: agreed, historical incidents keep their targets.
* **`ServiceNotFound`**: treated like `NO_POLICY` with a different reason. It cannot happen for real incidents, because
  P2's `V21` added the foreign key from `incidents` to `it_services`; it is kept as a safeguard.
* **Cross-priority consistency** (P1 targets never looser than P2): P4 does not need the backend to enforce it. Each
  incident uses the policy for its own priority. Keeping it a UI rule is fine.

### Storage (`V40`)

`incident_sla`, one row per incident:

| Column | Notes |
|---|---|
| `incident_id` | PK, FK `incidents (id)` |
| `priority`, `service_id`, `clock_start` | what the targets were resolved for; `clock_start` = the incident's `created_at` |
| `policy_id`, `policy_scope` | which policy supplied the targets (`SERVICE` or `GLOBAL`), null with `NO_POLICY` |
| `response_minutes`, `resolution_minutes`, `warning_threshold_pct` | the copied targets |
| `no_policy_reason` | `MISSING_SLA_CONFIG` or `SERVICE_NOT_FOUND`, set exactly when there are no targets |
| `response_due_at`, `resolution_due_at` | current deadlines (the resolution one includes pauses) |
| `response_warning_at`, `resolution_warning_at` | when the warning fires; `…_warned_at` records that it did |
| `response_met_at`, `resolution_met_at` | when each clock stopped |
| `response_breached_at`, `resolution_breached_at` | set once, dated at the deadline, never cleared |
| `paused_since`, `paused_seconds` | resolution pause bookkeeping |
| `response_status`, `resolution_status`, `status` | per clock `NO_POLICY`, `RUNNING`, `WARNING`, `PAUSED`, `MET`, `BREACHED`; `status` is the most serious of the two |
| `complete` | the incident is `VERIFIED` or `CLOSED`: no longer evaluated |
| `version`, `created_at`, `updated_at` | optimistic lock and timestamps |

CHECK constraints re-enforce these rules in the database.

### Monitor

`SlaMonitor` is a scheduled job (every 60 s, `app.sla.monitor.*`) annotated `@Transactional`, auditing as
`AuditActor.system("SLA_MONITOR")`. A run holds a PostgreSQL advisory lock, so a second application instance skips the run
instead of publishing every event twice. Each run:

1. creates SLA records for classified incidents that have none (and retries `NO_POLICY` ones);
2. applies state changes (pause, resume, met) since the last run;
3. raises warnings and breaches whose time has come, each exactly once.

Audit actions: `SLA_STARTED`, `SLA_WARNING_RAISED`, `SLA_BREACHED`, `SLA_MET`, `SLA_PAUSED`, `SLA_RESUMED`,
`SLA_RECALCULATED`, `SLA_POLICY_MISSING` (entity type `INCIDENT_SLA`, entity id = incident id). Escalation (PR 3) will add
P4 domain events for warnings and breaches (`SlaWarningRaised`, `SlaBreached`) for escalation and notifications to react to.

`@EnableScheduling` lives in P4's own `SlaSchedulingConfig`, so `ItSmApplication` is untouched. The test suite turns the
schedule off and calls `runAt(time)` directly.

**Until P2/P3 publish domain events** (section 6) the monitor polls the `incidents` table read-only, through one adapter
class (`sla/IncidentSnapshotReader`) that, with one assignee join in `SlaStore.list`, is the only P4 code aware of that table. Pause times are then accurate to the
polling interval. When the events exist, the adapter is replaced and the rest of the module is unchanged.

## 3. Escalation

Implemented in `escalation/` (PR 3). Escalation **records and notifies; it never reassigns** (reassigning stays a human
decision through P3). The notifications themselves come with section 4, which reads the escalation log.

### Path

Technician (assignee) → `UserDirectory.escalationChain(assignee)` in order (nearest team lead first; P1 already skips
inactive managers) → `UserDirectory.listAdmins()` (system admin and IT manager are both `ADMIN`).

| Tier | Goes to |
|---|---|
| `TEAM_LEAD` | the first manager in the chain, or the admins if there is none (or no assignee) |
| `NEXT_LEVEL` | the second manager in the chain, or the admins if the chain is shorter |
| `ADMINS` | every active admin |

### Triggers

Only **open** incidents escalate (`CLASSIFIED`, `ASSIGNED`, `ACKNOWLEDGED`, `IN_PROGRESS`, `PENDING_INFO`). Each trigger
fires **at most once per incident** (a UNIQUE constraint backs this), so a reassignment or a restart never repeats one.

| Trigger | When | Tier |
|---|---|---|
| `RESPONSE_BREACHED` | the SLA monitor recorded a response breach | `TEAM_LEAD` |
| `RESOLUTION_BREACHED` | the SLA monitor recorded a resolution breach | `TEAM_LEAD` |
| `RESOLUTION_OVERDUE` | the resolution clock has used `secondLevelPct` (default 150 %) of its target | `NEXT_LEVEL` |
| `RESOLUTION_CRITICAL` | ... `adminLevelPct` (default 200 %) of its target | `ADMINS` |
| `UNASSIGNED` | still `CLASSIFIED` `unassignedMinutes` (default 30) after it was reported | `ADMINS` |

* Paused time does not count towards the percentages, exactly as for the SLA deadline, and a paused clock is judged at the
  start of its pause.
* A warning escalates nobody; the assignee will be notified (section 4).
* P3's `NO_ELIGIBLE_TECHNICIAN` outcome is not stored anywhere P4 can read, so it is covered by `UNASSIGNED` (the incident
  stays `CLASSIFIED`). An `IncidentAssignmentFailed` event (section 6) would let it escalate immediately.
* An escalation with nobody to go to (no team lead and no active admin) is still recorded, with no targets, so it is not
  retried every minute.
* Deferred to notifications: flagging **SLA risk early** from `TechnicianWorkloadProvider` (an overloaded assignee past 50 %
  of the target). It is a notification, not an escalation.

### Monitor

`EscalationMonitor` runs every 60 s after the SLA monitor (`app.escalation.monitor.*`), reading the SLA facts it
committed, so a breach escalates within one polling interval. One run is one `@Transactional` pass under its own
PostgreSQL advisory lock. Each escalation publishes `INCIDENT_ESCALATED` (entity `INCIDENT`) as
`AuditActor.system("ESCALATION_MONITOR")`, with the trigger, tier, target user ids and assignee in its metadata.

### Settings (answers P1's open question 3)

**P4 owns `unassignedEscalationMinutes`**, stored with the two percentages in the `escalation_settings` singleton (`V41`),
behind `GET/PUT /api/admin/escalation-settings` (`SLA_CONFIGURE`; versioned, audited as `ESCALATION_SETTINGS_UPDATED`). The
`SecurityConfig` rule for that path was added in PR 3 next to the SLA policies' rule, for P1 to review. The admin
workspace has an "Escalation" page for it.

### History

`GET /api/incidents/{id}/escalations` lists an incident's escalations with the names of the people it went to, for IT staff
(technicians and admins) whom P2's `IncidentAccessPolicy` lets see the incident. Reporters do not see it. The incident page
shows it in the "Service level" card.

### Storage (`V41`)

`escalation_settings` (one row) and `incident_escalations` (append-only, enforced by a trigger: incident, trigger, tier,
target user ids, assignee, created at; UNIQUE per incident and trigger).

## 4. Notifications

Implemented in `notification/` (PR 4).

### Channels

A channel is an interface; a new channel is a new class, and the service that picks channels never changes:

```kotlin
interface NotificationChannel { val key: ChannelKey; val transactional: Boolean; fun deliver(notification: Notification) }
```

* `IN_APP` (`InAppChannel`): the notification is stored in the user's inbox, **inside** the business transaction, so it
  commits with the change it reports, or not at all.
* `EMAIL`, `SMS` (`SimulatedEmailChannel`, `SimulatedSmsChannel`): **simulated**, as `PRODUCT.md` says. They log that a
  message would be sent (recipient id and type only: no address, no text). They run only **after commit**, so a rolled-back
  change notifies nobody, and a failure is logged, never propagated.
* **Channel by priority** (`ChannelPolicy`): P1 → in-app + email + SMS; P2 → in-app + email; P3, P4 and no priority →
  in-app only. The channels used are stored with each notification.

### Who is told what

| Event | Source | Who is notified |
|---|---|---|
| Assigned / reassigned | polling | the new assignee (`INCIDENT_ASSIGNED`); the reporter (`ASSIGNMENT_MADE`) unless they are the assignee |
| Info requested (`PENDING_INFO`) | polling | the reporter (`INFO_REQUESTED`) |
| Resolved | polling | the reporter (`INCIDENT_RESOLVED`: please confirm the fix) |
| Reopened (`RESOLVED` → working) | polling | the assignee (`INCIDENT_REOPENED`) |
| SLA warning, SLA breach | SLA monitor event | the assignee (`SLA_WARNING`, `SLA_BREACHED`), with the deadline |
| No SLA policy | SLA monitor event | every active admin (`SLA_POLICY_MISSING`) |
| Escalated | escalation monitor event | everyone it reached (`ESCALATED`), with the reason |

* **SLA and escalation** notifications come from P4's own events (`SlaNotice`, `EscalationRecorded`), published inside the
  monitors' transactions and handled synchronously, so they fire exactly once, with the change.
* **Lifecycle** notifications come from polling until P2/P3 publish domain events (section 6): `NotificationMonitor`
  (every 30 s, `app.notification.monitor.*`, own advisory lock) compares each incident with the state and assignee P4
  last saw (`notification_watch`) and notifies each change once. Accurate to one interval: two moves between runs show as
  the net change. An incident seen for the first time is a **silent baseline** (deploying this must not flood inboxes),
  except a fresh assignment (`ASSIGNED` within the last 15 minutes), which is still news.
* Not built (yet): "incident classified" to the reporter (they have just reported it themselves), and the early **SLA-risk**
  notice from `TechnicianWorkloadProvider` (an overloaded assignee past 50 % of the target). Both are small follow-ups.

### Storage (`V42`)

`notifications` (recipient, type, incident, priority, title, body, channels, created at, read at). A trigger lets only
`read_at` change, once, from empty; rows are never deleted. `notification_watch` (incident, last state, last assignee) is
the polling bookkeeping.

### API and frontend

`GET /api/notifications?unreadOnly&page&size` (own only, newest first, paged), `GET /api/notifications/unread-count`,
`POST /api/notifications/{id}/read` (idempotent; someone else's id is a 404), `POST /api/notifications/read-all`.
Any signed-in user, each seeing only their own. The top bar has a bell with the unread count and the latest five, and
`/notifications` is the full inbox. The mock frontend keeps a small demo inbox per account.

## 5. Analytics

Read-only, `ANALYTICS_VIEW` (admins), under `/api/admin/analytics/*`, every query filtered by a date range:

* SLA compliance (met vs breached) by priority, service and category;
* mean and 90th-percentile time to respond and to resolve;
* breach and escalation counts over time;
* open incidents by state and priority, unassigned count;
* technician workload (from `TechnicianWorkloadProvider`) and average feedback rating (from P3's `incident_feedback`).

Plain aggregate SQL first. `V43` only if a query needs an index or a view.

## 6. Domain events P4 asks P2 and P3 to publish (Proposed)

Audit is a record, not a message bus, so P4 needs its own events. Proposed shape, in `common/event` (a P1-reviewed PR):

| Event | Published by | When | Fields |
|---|---|---|---|
| `IncidentClassified` | P2 | `CLASSIFY` committed | incidentId, serviceId, categoryId, priority, occurredAt |
| `IncidentStateChanged` | P3 | every transition | incidentId, from, to, transition, actorId, occurredAt |
| `IncidentAssigned` | P3 | assign and reassign | incidentId, assigneeId, previousAssigneeId, occurredAt |
| `IncidentAssignmentFailed` | P3 | outcome `NO_ELIGIBLE_TECHNICIAN` | incidentId, occurredAt |
| `IncidentPriorityChanged` | whoever writes the priority | override or recalculation | incidentId, from, to, actorId, occurredAt |

* Published with Spring's `ApplicationEventPublisher` **inside** the business transaction.
* P4's SLA listeners run `BEFORE_COMMIT` (the SLA row commits with the change); notification listeners run `AFTER_COMMIT`.
* Events are immutable data classes holding ids only, never entities or personal data.

## 7. Migrations

`V40` SLA (merged), `V41` escalation, `V42` notifications (PR 4), `V43` analytics (only if needed). All reference `incidents (id)`
and `users (id)`, which exist from `V20` and `V1`. Migrations are never edited after merge.

P2's `V22` (impact and urgency) was merged after `V40`. Flyway runs in strict order (`docs/migrations.md` section 2), so a
database that already had `V40` refuses to start until it is reset once (`docker compose down -v`); fresh databases and CI
are unaffected.
