## 1. Priority

Priority is computed **once, when an incident is reported**: P2's intake creates incidents directly in `CLASSIFIED`, so
reporting and classifying are the same step. It comes from what the reporter says and what the service catalog knows. It is a pure function, so the same inputs always give the same priority and every result can be explained.

### Inputs

| Input | Values | Source |
|---|---|---|
| Impact: how many people are affected | `HIGH` (organisation-wide or many users), `MEDIUM` (a department or team), `LOW` (one person) | the reporter, answering "How many people are affected?" on the report form |
| Urgency: how soon it hurts | `HIGH` (work has stopped, no workaround), `MEDIUM` (degraded, a workaround exists), `LOW` (an inconvenience) | the reporter, answering "Can you still work?" |
| Business criticality of the service | 1 (low) to 5 (mission critical) | P1 `ServiceCatalog.findById(id).businessCriticality` |
| Dependent services | number of **active** services that depend on this one, directly or transitively | P1 `ServiceCatalog.listActive()`: the reverse graph is built in memory, so one call covers the whole walk |

`Impact` and `Urgency` are shared vocabulary (P2 stores them, P4 reads them), so they live in `common/model` next to
`Priority`.

### Algorithm

1. **Effective impact.** If **3 or more active services** depend on the incident's service (transitively), raise impact by one
   level, at most `HIGH`. An outage of a shared service spreads.
2. **Base priority** from the ITIL impact × urgency matrix, using the effective impact:

   | Impact \ Urgency | HIGH | MEDIUM | LOW |
   |---|---|---|---|
   | **HIGH** | P1 | P2 | P3 |
   | **MEDIUM** | P2 | P3 | P4 |
   | **LOW** | P3 | P4 | P4 |

3. **Criticality adjustment**, at most one level, never past `P1` or `P4`:
   * criticality **5** (mission critical): one level more urgent;
   * criticality **1** (low): one level less urgent;
   * 2 to 4: no change.

The result carries the base priority and a list of plain-language reasons (for the audit trail and the UI), for example
`Impact raised from MEDIUM to HIGH: 4 services depend on Campus Wi-Fi` and `Raised from P2 to P1: Campus Wi-Fi has business
criticality 5`.

Worked examples:

| Impact | Urgency | Criticality | Dependents | Result |
|---|---|---|---|---|
| HIGH | HIGH | 3 | 0 | P1 |
| MEDIUM | HIGH | 5 | 0 | P2 → **P1** |
| MEDIUM | MEDIUM | 3 | 4 | impact → HIGH, **P2** |
| HIGH | HIGH | 1 | 0 | P1 → **P2** |
| LOW | LOW | 5 | 0 | P4 → **P3** |

The thresholds (3 dependents, criticality 5 and 1) are **tunable constants, not from the spec**. They are in one place
(`priority/PriorityCalculator`) and covered by tests at every boundary.

### Contract (implemented)

P4 provides an SPI in `common/spi`; `priority/CatalogPriorityPolicy` is the only implementation:

```kotlin
interface PriorityPolicy {
    /** @throws ServiceNotFound if [serviceId] is unknown. An inactive service is still assessed. */
    fun assess(serviceId: Long, impact: Impact, urgency: Urgency): PriorityAssessment
}
```

* **P2's intake** calls it for every new incident. `POST /api/incidents` takes `impact` and `urgency`, **never a
  priority**, so a reporter cannot choose P1. P2 stores the returned `priority` plus the answers (`incidents.impact` /
  `urgency`, `V22`) so a later recalculation has its inputs, and puts the reasons in `INCIDENT_CLASSIFIED` as
  `priorityReasons`. Full contract: the integration guide, "P2: incident intake".
* `ServiceNotFound` is an answer, not a failure: it does not mark the caller's transaction rollback-only.
* The mock frontend service copies the matrix only for offline demos; the live app always asks the backend.
* **Later priority changes:** see "Changing a priority" below.

### Changing a priority (`V44`)

An admin can change an open incident's priority (`CLASSIFIED` to `PENDING_INFO`), with a reason:
`POST /api/incidents/{id}/priority` `{priority, reason}` (`INCIDENT_ASSIGN`, so admins). P2 owns `incidents.priority`, so
the endpoint is P2's (`intake/IncidentPriorityService`). It writes the column, audits `INCIDENT_PRIORITY_CHANGED` (previous
and new priority, the reason), and publishes `IncidentPriorityChanged`. P4 reacts after commit: the SLA is re-evaluated
with the new priority's targets (section 2, "Pauses and changes"), and the assignee is told (`PRIORITY_CHANGED`) unless
they made the change. 400 for an unknown or unchanged priority, a missing reason (at most 500 characters) or an
incident that is not being worked on; 404 for an unknown one. The incident page offers **Change priority** to admins.

## 2. SLA tracking

Implemented in `sla/` (#15); the API is documented in the integration guide, "SLA tracking".

### What is measured

| Clock | Starts | Stops (met) | Target |
|---|---|---|---|
| **Response** | `created_at` | `first_response_at` (the first `ACKNOWLEDGE`, never cleared) | `SlaPolicyView.responseTarget` |
| **Resolution** | `created_at` | `resolved_at` | `SlaPolicyView.resolutionTarget` |

* Clocks run from when the incident was **reported** (`created_at`): that is what the reporter experiences. P4 creates the
  SLA record as soon as P2's `IncidentClassified` event commits (or, if that reaction failed, at the next monitor run), and
  dates the deadlines from `created_at`.
* Targets are **copied** from the policy when tracking starts, so a later policy edit does not move existing deadlines.
* **24×7 calendar.** No business hours or holidays (out of scope for the course project; noted as a later extension).
* **Warning** when `warningThresholdPct` (default 80) of a target has elapsed and the clock has not stopped.
* **Breach** when the deadline passes and the clock has not stopped. A breach is recorded once and never removed, even if
  the clock later stops or a recalculation would move the deadline.

### Pauses and changes (answers P3's question)

| Event | Response clock | Resolution clock |
|---|---|---|
| `REQUEST_INFO` → `PENDING_INFO` | not affected (already met: the incident was acknowledged) | **paused** while waiting on the reporter |
| `PROVIDE_INFO` → `IN_PROGRESS` | n/a | resumes; the deadline moves later by the paused time |
| `RESOLVE` | n/a | stops (met or breached) |
| `REOPEN` | stays met | **resumes**; the time spent in `RESOLVED` counts as paused (the reporter had been told it was fixed) |
| `REASSIGN` | no change (`first_response_at` is never cleared) | no change |
| Priority changed (`V44`) | met or breached: deadline kept. Tighter target: the earlier of the old deadline and (the change + the new target). Looser: `created_at` + the new target | same, pauses included |
| `VERIFY`, `CLOSE` | no change | no change |

### When no policy applies (answers P1's question)

* `SlaPolicyProvider.resolve` answering **422 `MISSING_SLA_CONFIG`**: P4 records the SLA as `NO_POLICY`, publishes
  `SLA_POLICY_MISSING` once, and retries on every monitor run until a policy exists (notifying admins comes with
  notifications, section 4). The incident flow is
  never blocked. P4 does not invent a duration.
* **Inactive service still resolves**: agreed, historical incidents keep their targets.
* **`ServiceNotFound`**: treated like `NO_POLICY` with a different reason. It cannot happen for real incidents, because
  P2's `V21` added the foreign key from `incidents` to `it_services`; it is kept as a safeguard.
* **Cross-priority consistency** (P1 targets never looser than P2): P4 does not need the backend to enforce it. Each
  incident uses the policy for its own priority. Keeping it a UI rule is fine.

### Storage (`V40`)

`incident_sla`, one row per incident:

| Column | Notes |
|---|---|
| `incident_id` | PK, FK `incidents (id)` |
| `priority`, `service_id`, `clock_start` | what the targets were resolved for; `clock_start` = the incident's `created_at` |
| `policy_id`, `policy_scope` | which policy supplied the targets (`SERVICE` or `GLOBAL`), null with `NO_POLICY` |
| `response_minutes`, `resolution_minutes`, `warning_threshold_pct` | the copied targets |
| `no_policy_reason` | `MISSING_SLA_CONFIG` or `SERVICE_NOT_FOUND`, set exactly when there are no targets |
| `response_due_at`, `resolution_due_at` | current deadlines (the resolution one includes pauses) |
| `response_warning_at`, `resolution_warning_at` | when the warning fires; `…_warned_at` records that it did |
| `response_met_at`, `resolution_met_at` | when each clock stopped |
| `response_breached_at`, `resolution_breached_at` | set once, dated at the deadline, never cleared |
| `paused_since`, `paused_seconds` | resolution pause bookkeeping |
| `response_status`, `resolution_status`, `status` | per clock `NO_POLICY`, `RUNNING`, `WARNING`, `PAUSED`, `MET`, `BREACHED`; `status` is the most serious of the two |
| `complete` | the incident is `VERIFIED` or `CLOSED`: no longer evaluated |
| `version`, `created_at`, `updated_at` | optimistic lock and timestamps |

CHECK constraints re-enforce these rules in the database.

### Monitor

`SlaMonitor` is a scheduled job (every 60 s, `app.sla.monitor.*`) annotated `@Transactional`, auditing as
`AuditActor.system("SLA_MONITOR")`. A run holds a PostgreSQL advisory lock, so a second application instance skips the run
instead of publishing every event twice. Each run:

1. creates SLA records for classified incidents that have none (and retries `NO_POLICY` ones);
2. applies state changes (pause, resume, met) since the last run;
3. raises warnings and breaches whose time has come, each exactly once;
4. raises predicted misses (see "Predictive risk" below), each at most once per incident.

Audit actions: `SLA_STARTED`, `SLA_WARNING_RAISED`, `SLA_BREACHED`, `SLA_MET`, `SLA_PAUSED`, `SLA_RESUMED`,
`SLA_RECALCULATED`, `SLA_POLICY_MISSING`, `SLA_RISK_PREDICTED` (entity type `INCIDENT_SLA`, entity id = incident id).
Warnings, breaches, missing policies and predicted misses are also published as `SlaNotice` for notifications.

`@EnableScheduling` lives in P4's own `SlaSchedulingConfig`, so `ItSmApplication` is untouched. The test suite turns the
schedule off and calls `runAt(time)` directly.

**Events and the sweep.** `SlaEventListener` evaluates one incident (`SlaMonitor.evaluateIncident`) right after each
`IncidentClassified` or `IncidentStateChanged` commits, so tracking starts at once and pauses, resumes and stops carry the
exact time of the change. It waits for the advisory lock instead of skipping, runs in its own transaction, and logs a
failure instead of throwing it at P2/P3. The every-minute run stays: warnings and breaches happen because time passes,
with no event, and it catches any change whose reaction failed. Both read the `incidents` table read-only through one
adapter (`sla/IncidentSnapshotReader`) which, with one assignee join in `SlaStore.list`, is the only P4 code aware of
that table.

### Predictive risk (`V43`)

The fixed warning fires at a set share of the target (say 80 %), which can be too late to help. **Predictive risk** warns
earlier when an incident is unlikely to make its resolution deadline, judged from how long similar incidents actually took.
It is a step of every SLA sweep (`SlaRiskDetector`, after the clocks), and the rules are pure (`SlaRiskModel`):

1. **Candidates:** open incidents whose resolution clock is `RUNNING`. A clock already in `WARNING`, `PAUSED`, `MET` or
   `BREACHED` is skipped (it already says more), and an incident is flagged at most once.
2. **Similar incidents:** resolution clocks met in the last 180 days (`app.sla.risk.history-days`), from P4's own
   `incident_sla`, pauses excluded: the same priority and category if there are at least 5, else the same priority if
   there are at least 5. Fewer: **no forecast**; P4 does not guess.
3. **Remaining time:** among the similar incidents that took longer than this one has run so far, the median of what they
   still needed after that point. If fewer than 3 took longer, the incident is unusual and is assumed to need a typical
   (median) incident's whole time again.
4. **Assignee load:** above their configured ceiling, the remaining time is multiplied by their load (active incidents from
   P3's `TechnicianWorkloadProvider` / `maxWorkload` from P1's `UserDirectory`), at most ×3. Under the ceiling, or nobody
   assigned: no change. Without either provider, the forecast is made without it.
5. **Predicted miss:** now + remaining time is after the resolution deadline. P4 then records it once in
   `incident_sla_risk` (append-only: deadline, predicted time, basis, sample size, typical remaining minutes, load factor,
   assignee), audits `SLA_RISK_PREDICTED`, and notifies the assignee, or every active admin when nobody has it
   (`SLA_AT_RISK`).

The SLA API adds `risk` (null unless predicted) to `GET /api/incidents/{id}/sla` and `GET /api/sla/incidents`; the
"Service level" card shows it as a **Forecast: Likely to miss** line with the predicted time and what it was based on,
while the resolution clock is running or warned. The clock's own status does not change: a prediction is not a breach.
The flag is not withdrawn if things later speed up; the clock's status shows how it actually goes.

### On the incident list

Searching and filtering incidents is P3's list (`GET /api/incidents` and the Incidents page: text, state, priority,
category, service, technician, dates, SLA status). P4 adds its SLA facts to it rather than a second search page:

* each row carries `sla` (overall and resolution status, resolution deadline, `predictedMiss`), shown to staff as a
  **Resolution due** column ("Due in 1 h 5 min", flagged **At risk**, **Likely to miss** or **Breached** in words);
* `sort=DEADLINE` lists the nearest resolution deadline first (the **Deadline** toggle beside P3's priority sort);
* `predictedMiss=true` filters to predicted misses;
* `slaAttention` counts breached, at-risk and predicted-miss incidents under every filter except the SLA ones, shown to
  staff as **Service level** quick filters (Breached 4, At risk 1, Predicted to miss 0) that apply the filter.

The SQL lives in P3's `JpaIncidentStore`, reading `incident_sla` and `incident_sla_risk` read-only, like its existing
`slaStatus` filter. Reporters' list is unchanged.

## 3. Escalation

Implemented in `escalation/` (PR 3). Escalation **records and notifies; it never reassigns** (reassigning stays a human
decision through P3). The notifications themselves come with section 4, which reads the escalation log.

### Path

Technician (assignee) → `UserDirectory.escalationChain(assignee)` in order (nearest team lead first; P1 already skips
inactive managers) → `UserDirectory.listAdmins()` (system admin and IT manager are both `ADMIN`).

| Tier | Goes to |
|---|---|
| `TEAM_LEAD` | the first manager in the chain, or the admins if there is none (or no assignee) |
| `NEXT_LEVEL` | the second manager in the chain, or the admins if the chain is shorter |
| `ADMINS` | every active admin |

### Triggers

Only **open** incidents escalate (`CLASSIFIED`, `ASSIGNED`, `ACKNOWLEDGED`, `IN_PROGRESS`, `PENDING_INFO`). Each trigger
fires **at most once per incident** (a UNIQUE constraint backs this), so a reassignment or a restart never repeats one.

| Trigger | When | Tier |
|---|---|---|
| `RESPONSE_BREACHED` | the SLA monitor recorded a response breach | `TEAM_LEAD` |
| `RESOLUTION_BREACHED` | the SLA monitor recorded a resolution breach | `TEAM_LEAD` |
| `RESOLUTION_OVERDUE` | the resolution clock has used `secondLevelPct` (default 150 %) of its target | `NEXT_LEVEL` |
| `RESOLUTION_CRITICAL` | ... `adminLevelPct` (default 200 %) of its target | `ADMINS` |
| `UNASSIGNED` | still `CLASSIFIED` `unassignedMinutes` (default 30) after it was reported | `ADMINS` |

* Paused time does not count towards the percentages, exactly as for the SLA deadline, and a paused clock is judged at the
  start of its pause.
* A warning escalates nobody; the assignee will be notified (section 4).
* P3's `NO_ELIGIBLE_TECHNICIAN` outcome is not stored anywhere P4 can read, so it is covered by `UNASSIGNED` (the incident
  stays `CLASSIFIED`). When P3 publishes `IncidentAssignmentFailed` (section 6), `EscalationEventListener` escalates `UNASSIGNED` at once
  instead of after `unassignedMinutes` (audit metadata `reason: NO_ELIGIBLE_TECHNICIAN`).
* An escalation with nobody to go to (no team lead and no active admin) is still recorded, with no targets, so it is not
  retried every minute.
* Flagging **SLA risk early** is a notification, not an escalation: see "Predictive risk" in section 2.

### Monitor

`EscalationMonitor` runs every 60 s after the SLA monitor (`app.escalation.monitor.*`), reading the SLA facts it
committed, so a breach escalates within one polling interval (escalation is time-driven, so this stays a sweep; only the
failed-assignment case reacts to an event). One run is one `@Transactional` pass under its own
PostgreSQL advisory lock. Each escalation publishes `INCIDENT_ESCALATED` (entity `INCIDENT`) as
`AuditActor.system("ESCALATION_MONITOR")`, with the trigger, tier, target user ids and assignee in its metadata.

### Settings (answers P1's open question 3)

**P4 owns `unassignedEscalationMinutes`**, stored with the two percentages in the `escalation_settings` singleton (`V41`),
behind `GET/PUT /api/admin/escalation-settings` (`SLA_CONFIGURE`; versioned, audited as `ESCALATION_SETTINGS_UPDATED`). The
`SecurityConfig` rule for that path was added in PR 3 next to the SLA policies' rule, for P1 to review. The admin
workspace has an "Escalation" page for it.

### History

`GET /api/incidents/{id}/escalations` lists an incident's escalations with the names of the people it went to, for IT staff
(technicians and admins) whom P2's `IncidentAccessPolicy` lets see the incident. Reporters do not see it. The incident page
shows it in the "Service level" card.

### Storage (`V41`)

`escalation_settings` (one row) and `incident_escalations` (append-only, enforced by a trigger: incident, trigger, tier,
target user ids, assignee, created at; UNIQUE per incident and trigger).

## 4. Notifications

Implemented in `notification/` (PR 4).

### Channels

A channel is an interface; a new channel is a new class, and the service that picks channels never changes:

```kotlin
interface NotificationChannel { val key: ChannelKey; val transactional: Boolean; fun deliver(notification: Notification) }
```

* `IN_APP` (`InAppChannel`): the notification is stored in the user's inbox, **inside** the business transaction, so it
  commits with the change it reports, or not at all.
* `EMAIL`, `SMS` (`SimulatedEmailChannel`, `SimulatedSmsChannel`): **simulated**, as `PRODUCT.md` says. They log that a
  message would be sent (recipient id and type only: no address, no text). They run only **after commit**, so a rolled-back
  change notifies nobody, and a failure is logged, never propagated.
* **Channel by priority** (`ChannelPolicy`): P1 → in-app + email + SMS; P2 → in-app + email; P3, P4 and no priority →
  in-app only. The channels used are stored with each notification.

### Who is told what

| Event | Source | Who is notified |
|---|---|---|
| Assigned / reassigned | P3 event | the new assignee (`INCIDENT_ASSIGNED`); the reporter (`ASSIGNMENT_MADE`) unless they are the assignee |
| Info requested (`PENDING_INFO`) | P3 event | the reporter (`INFO_REQUESTED`) |
| Resolved | P3 event | the reporter (`INCIDENT_RESOLVED`: please confirm the fix) |
| Reopened (`RESOLVED` → working) | P3 event | the assignee (`INCIDENT_REOPENED`) |
| SLA warning, SLA breach | SLA monitor event | the assignee (`SLA_WARNING`, `SLA_BREACHED`), with the deadline |
| No SLA policy | SLA monitor event | every active admin (`SLA_POLICY_MISSING`) |
| Predicted to miss the resolution deadline | SLA monitor event | the assignee, or every active admin when nobody has it (`SLA_AT_RISK`), with the deadline and the predicted time |
| Escalated | escalation monitor event | everyone it reached (`ESCALATED`), with the reason |
| Priority changed | P2 event | the assignee, unless they changed it (`PRIORITY_CHANGED`) |

* **SLA and escalation** notifications come from P4's own events (`SlaNotice`, `EscalationRecorded`), published inside the
  monitors' transactions and handled synchronously, so they fire exactly once, with the change.
* **Lifecycle** notifications are sent right after P2/P3's events commit (`IncidentNotificationListener`, section 6):
  `NotificationMonitor.processIncident` compares the incident with the state and assignee P4 last saw
  (`notification_watch`) and notifies the change once. P2's `IncidentClassified` records the baseline, so later changes
  are real changes. The same comparison runs as a sweep every 5 minutes (`app.notification.monitor.*`, own advisory lock)
  as the safety net for a change whose reaction failed; the watch row means nothing is sent twice. A change only the sweep
  catches is accurate to one interval: two moves between runs show as the net change. An incident seen for the first time is a **silent baseline** (deploying this must not flood inboxes),
  except a fresh assignment (`ASSIGNED` within the last 15 minutes), which is still news.
* Not built: "incident classified" to the reporter (they have just reported it themselves).

### Storage (`V42`)

`notifications` (recipient, type, incident, priority, title, body, channels, created at, read at). A trigger lets only
`read_at` change, once, from empty; rows are never deleted. `notification_watch` (incident, last state, last assignee) is
the bookkeeping that makes each change notified once, whether an event or the sweep notices it.

### API and frontend

`GET /api/notifications?unreadOnly&page&size` (own only, newest first, paged), `GET /api/notifications/unread-count`,
`POST /api/notifications/{id}/read` (idempotent; someone else's id is a 404), `POST /api/notifications/read-all`.
Any signed-in user, each seeing only their own. The top bar has a bell with the unread count and the latest five, and
`/notifications` is the full inbox. The mock frontend keeps a small demo inbox per account.

## 5. Analytics

Implemented in `analytics/` (PR 5): one read-only endpoint, `GET /api/admin/analytics/summary?from&to`, for
`ANALYTICS_VIEW` (admins; its `SecurityConfig` rule was added in PR 5 for P1 to review), and the admin workspace's
"Analytics" page.

* **Range:** inclusive UTC days, default the last 30, at most 366; a backwards or longer range is a 400 with field errors.
* **Reported in the range drives SLA compliance and times**, so a slow incident counts against the period it was reported
  in. "Open now" and "not assigned now" are a snapshot, whatever the range.

| Figure | Definition |
|---|---|
| Reported / resolved | incidents whose `created_at` / `resolved_at` falls in the range |
| Open now, by state and priority; not assigned now | current open incidents; `CLASSIFIED` ones |
| SLA compliance (overall, by priority, service, category) | over incidents reported in the range with a policy: met = clock `MET` and never breached; breached = a recorded breach (a breach counts even if the clock later stopped). Percentage = met / (met + breached), one decimal; empty while nothing is decided |
| Time to respond / resolve | mean and 90th percentile (`percentile_cont`) of `first_response_at` / `resolved_at` minus `created_at`, for incidents reported in the range: elapsed time, pauses included |
| Escalations | `incident_escalations` in the range, by trigger |
| Per day | reported, resolved, SLA breaches (each clock's breach on its day) and escalations, per UTC day |
| Technicians | usable technicians: open incidents now (from P3's `TechnicianWorkloadProvider`) against their maximum, incidents they resolved in the range, and the count and average of the ratings their incidents received in the range (P3's `incident_feedback`) |

* All reporting SQL is in one class, `AnalyticsQueries`: the one place that reads across modules' tables, read-only.
  Plain aggregate SQL on existing indexes; no migration was needed.
* **Frontend:** a date-range row (last 7 / 30 / 90 days, or a custom range) scoping everything below; stat tiles; per-day
  columns (one series each, keyboard-readable, with a hover and focus tooltip); compliance meters by priority; escalations as
  ranked bars; tables by service, by category and per technician; and a "Show as tables" switch that gives every chart a
  table twin. Charts use the theme accent only (validated against the card surface), following the dataviz rules.

## 6. Domain events (implemented)

Audit is a record, not a message bus, so modules that must react to an incident change listen to domain events. The
classes live in `common/event/IncidentEvents.kt` (P1 reviews `common`); P2 and P3 publish them from their own services.

| Event | Published by | When | Fields |
|---|---|---|---|
| `IncidentClassified` | P2, `IncidentIntakeService.create` | a report is accepted (intake creates incidents directly in `CLASSIFIED`) | incidentId, reporterId, serviceId, categoryId, priority, occurredAt |
| `IncidentStateChanged` | P3, `IncidentLifecycleService.transition` and `IncidentAssignmentService` | every transition, including `ASSIGN` and `REASSIGN` | incidentId, fromState, toState, transition, actorId, occurredAt |
| `IncidentAssigned` | P3, `IncidentAssignmentService` | assign and reassign, right after the matching `IncidentStateChanged` | incidentId, assigneeId, previousAssigneeId, actorId, occurredAt |
| `IncidentAssignmentFailed` | P3, `IncidentAssignmentService.assignAutomatically` | outcome `NO_ELIGIBLE_TECHNICIAN` (not `MANUAL_REQUIRED`, which is a setting, not a failure) | incidentId, reason, occurredAt |
| `IncidentPriorityChanged` | P2, `IncidentPriorityService.change` | an admin changes an open incident's priority | incidentId, fromPriority, toPriority, actorId, occurredAt |

* Published with Spring's `ApplicationEventPublisher` **inside** the business transaction, after the change and its audit
  event are written. A refused or failed change publishes nothing.
* Ids, codes and state names only (states as `IncidentState` names in strings, because that enum is P3's), never entities,
  text or personal data.
* Listeners react `AFTER_COMMIT` in their own transaction and never throw back into the publisher, so a listener's
  failure cannot undo or fail someone else's change. (The earlier proposal had SLA listeners run `BEFORE_COMMIT`; that
  would let an SLA bug roll back an incident change, so it was dropped.)
* `IncidentPriorityChanged` (P2, `IncidentPriorityService.change`: incidentId, fromPriority, toPriority, actorId,
  occurredAt) is published when an admin changes an open incident's priority (section 1); P4 re-evaluates the SLA and
  tells the assignee.

**How P4 reacts** (PR 6b). Each listener is `@TransactionalEventListener(AFTER_COMMIT)`, calls a monitor method that runs
`REQUIRES_NEW` and waits for that monitor's advisory lock (so it never races a sweep), and catches and logs its own
failures. The sweeps stay as the safety net.

| Event | SLA (`SlaEventListener`) | Notifications (`IncidentNotificationListener`) | Escalation (`EscalationEventListener`) |
|---|---|---|---|
| `IncidentClassified` | start tracking | record the baseline (nobody is told) | |
| `IncidentStateChanged` | pause, resume, met, stop at the exact time | assigned, question, resolved, reopened | |
| `IncidentAssigned` | | (comes with `IncidentStateChanged`) | |
| `IncidentAssignmentFailed` | | | `UNASSIGNED` at once |

| Sweep | Interval | Why it stays |
|---|---|---|
| SLA | 60 s | warnings and breaches happen because time passes; retries failed reactions and missing policies |
| Escalation | 60 s | its triggers are time-driven (breaches, percentages, unassigned wait) |
| Notifications | 5 min (was 30 s) | only catches a change whose reaction failed |

`P4_EVENT_LISTENERS_ENABLED=false` (`app.p4.event-listeners.enabled`) turns the reactions off; the sweeps then do
everything, later. The test suite turns them off for other modules' tests; `IncidentEventReactionsIntegrationTest` turns
them on.

## 7. Migrations

`V40` SLA, `V41` escalation, `V42` notifications, `V43` predictive SLA risk (`incident_sla_risk`, plus `SLA_AT_RISK` in the
notification type check), `V44` priority changes (a per-clock deadline shift on `incident_sla`, plus `PRIORITY_CHANGED`).
Analytics needed no migration; `V45`-`V49` stay free. All reference `incidents (id)`
and `users (id)`, which exist from `V20` and `V1`. Migrations are never edited after merge.

P2's `V22` (impact and urgency) was merged after `V40`. Flyway runs in strict order (`docs/migrations.md` section 2), so a
database that already had `V40` refuses to start until it is reset once (`docker compose down -v`); fresh databases and CI
are unaffected.
