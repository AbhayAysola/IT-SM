## Lifecycle

`NEW → CLASSIFIED → ASSIGNED → ACKNOWLEDGED → IN_PROGRESS ⇄ PENDING_INFO`, then `IN_PROGRESS → RESOLVED → VERIFIED → CLOSED`
(terminal). `RESOLVED → IN_PROGRESS` is `REOPEN`; `REASSIGN` returns any active state to `ASSIGNED`.
The rules are one table, `IncidentTransition`; `IncidentStateMachine.apply` validates a move.

| Move | From | To | Needs | Reason |
|---|---|---|---|---|
| `CLASSIFY` | NEW | CLASSIFIED | `INCIDENT_CREATE` | |
| `ASSIGN` | CLASSIFIED | ASSIGNED | `INCIDENT_ASSIGN` | |
| `REASSIGN` | ASSIGNED, ACKNOWLEDGED, IN_PROGRESS, PENDING_INFO | ASSIGNED | `INCIDENT_ASSIGN` | yes |
| `ACKNOWLEDGE` | ASSIGNED | ACKNOWLEDGED | `INCIDENT_WORK` | |
| `START_WORK` | ACKNOWLEDGED | IN_PROGRESS | `INCIDENT_WORK` | |
| `REQUEST_INFO` | IN_PROGRESS | PENDING_INFO | `INCIDENT_WORK` | yes |
| `PROVIDE_INFO` | PENDING_INFO | IN_PROGRESS | `INCIDENT_VIEW_OWN` | yes |
| `RESOLVE` | IN_PROGRESS | RESOLVED | `INCIDENT_WORK` | yes |
| `VERIFY` | RESOLVED | VERIFIED | `INCIDENT_VERIFY_OWN` | |
| `REOPEN` | RESOLVED | IN_PROGRESS | `INCIDENT_VERIFY_OWN` | yes |
| `CLOSE` | VERIFIED | CLOSED | `INCIDENT_CLOSE` | |

* `apply` throws in this order: `InvalidStateTransition` (409), `UnauthorizedOperation` (403), `InvalidInput` (400, reason
  missing or over 1000 chars). Legality first, so a caller acting on a stale incident learns it moved on.
* **Permission is not ownership.** The service must also check the caller is the assignee (work moves) or reporter
  (`PROVIDE_INFO`, `VERIFY`, `REOPEN`) via P2's `IncidentAccessPolicy`. Admins hold every permission and are exempt.
* `ASSIGNED`, `ACKNOWLEDGED`, `IN_PROGRESS`, `PENDING_INFO` count toward workload; `RESOLVED` does not.
* No state can get stuck (a test proves every state reaches `CLOSED`). No cancel state, no auto-close.
* SLA clocks are P4's (does `PENDING_INFO` pause the timer?). Concurrency is the service's job: version the row.

## Assignment

`AssignmentEngine.decide(settings, request, candidates)`: filter by `EligibilityPolicy` → pick the strategy (a category
override beats the global one) → rank → first wins. Candidates are plain snapshots (profile + active count + last
assignment), so it needs no P2 entity or P1 bean. `RegisteredAssignmentStrategyCatalog` implements the SPI P1 validates against.

| Key | Order | Notes |
|---|---|---|
| `LOAD_BASED` | lowest `active/max` | Seeded default (V15); the app refuses to start without it; also the fallback |
| `SKILL_BASED` | highest proficiency in the category | Drops the unskilled: nobody skilled means no assignment, never an unqualified pick |
| `ROUND_ROBIN` | never-assigned first, then longest since last assignment | Stateless (derived from `lastAssignedAt`), so safe across restarts and instances |
| `MANUAL` | load order, display only | Never auto-assigns; exists because the admin UI offers it |

* **Eligible** = available, not excluded (the current assignee on reassign), `active < max`. A non-positive own `maxWorkload`
  means "use the default" (assumption). Skill is not part of eligibility. Named manual assignments are *validated*:
  `TechnicianUnavailable` / `WorkloadExceeded` (409).
* **Outcomes**, not exceptions: `ASSIGNED`, `MANUAL_REQUIRED`, `NO_ELIGIBLE_TECHNICIAN` (incident stays `CLASSIFIED`; P4's escalation signal).
* An unregistered configured key falls back to `LOAD_BASED` with a warning and `fellBackFrom` set, so a config slip never blocks assignment.
* All comparators end in the technician id and use integer cross-multiplication for utilisation, so results are exact and order-independent.
* **Recommendations** (top 5, with plain-language reasons) are always computed, independent of the strategy:
  `score = 100·(wSkill·skill + wHeadroom·headroom + wExperience·experience)`, with skill = proficiency/5 (0.5 with no category),
  headroom = `1 − active/max`, experience = `min(years,10)/10`. Weights: P1/P2 `0.45/0.20/0.35`, P3/P4 `0.40/0.45/0.15`.
  **Placeholder numbers, not from the spec**; tune in `weightsFor`.

## Investigation timeline

An append-only, per-incident story (what was tried, questions to the reporter, how it was fixed). It complements, never
replaces, the audit trail. `InvestigationPolicy` holds the rules; `InvestigationLog` is the storage contract.

* **Manual entries** (`NOTE`, `FINDING`, `ACTION_TAKEN`; internal by default, shareable): technician or admin, in
  `ACKNOWLEDGED`, `IN_PROGRESS`, `PENDING_INFO`, `RESOLVED`. Body trimmed, 1 to 4000 chars. Check order: shape, state, permission.
* **Conversation entries** (`INFO_REQUEST`, `INFO_RESPONSE`, `RESOLUTION`, `REOPEN_REASON`, `REASSIGNMENT`) exist only as a side effect
  of the matching transition, so the timeline cannot disagree with the state. Every transition needing a reason produces one.
* **Visibility is enforced in the entry:** conversation entries are always reporter-visible, `REASSIGNMENT` is always internal.
  Reporters never receive internal entries. A technician who reports an incident holds `INCIDENT_WORK` and so sees its internal notes (open question).
* No edit or delete; enforce append-only in the DB too. Audit metadata carries the entry type and visibility, **never the text**.

## Feedback

Verifying and rating are separate: `VERIFY` says "fixed", the rating says how it went. Unhappy with the fix means `REOPEN`.

* **Who:** only the reporter (not a technician, not an admin: it is their own voice). **When:** `VERIFIED` or `CLOSED`. **Once**, final.
  Rating 1 to 5, optional comment up to 1000 chars. Order: who, state (`FeedbackNotAllowed` 409), duplicate (409), input (400, all fields together).
* `FeedbackStore` needs a **unique constraint on the incident id**: two racing submissions both pass the duplicate check; the constraint stops the second.
* Audit `INCIDENT_FEEDBACK_RECORDED` carries the rating only. Per-technician averages are P4's.

## Persistence

`V30__p3_investigation_entries.sql` and `V31__p3_incident_feedback.sql`, stored by `JpaInvestigationLog` and `JpaFeedbackStore`.
Both tables hold the incident id as a plain string (no FK to P2's table) and reference only `users`.

* The database re-enforces what the domain promises, so a bug or a manual insert cannot break it: append-only and final
  (triggers reject UPDATE, DELETE, TRUNCATE; shared function `p3_reject_mutation`), the visibility rule, state and type
  vocabularies, length and rating ranges, and one feedback row per incident (primary key).
* Writes are `MANDATORY`-transactional: they fail fast outside the transaction that changes the incident.
* Writes use `persist` + `flush`, not Spring Data `save`. `save` would `merge` an entity with an assigned id, and for an
  immutable entity that silently ignores a second feedback instead of failing. Errors are translated by `@Repository`, so a
  duplicate surfaces as 409 `DUPLICATE_RESOURCE` and a constraint violation as 400.
* Because the tables are append-only, tests cannot clean up: each uses its own user and incident id.

## Frontend (mock)

`/incidents` and `/incidents/[id]`, role-aware: employees see plain-language status, reply, verify or reopen, and rate; technicians
get a queue, actions, notes and past fixes for similar incidents; admins assign and reassign from the scored suggestions and close.

* Mock data is one demo set per signed-in account (`itsm_p3_v1_world_<email>`), built from the account's role. The technician
  pool comes from the admin workspace's mock technicians. `localStorage.itsm_p3_simulate_error = "1"` forces errors (tests only).
* `USER` and any unknown role are treated as employee, so against the real backend only the employee view is reachable today.
* Anyone else's incident is "not found", never "forbidden". `services/incident-service.ts` is the only thing pages call; replace it with the API.
* Dialogs restore focus themselves (Radix only does it for its own `DialogTrigger`); cards use real `h2` headings (`CardTitle` is a `div`).
* Reuses the admin workspace's toast, form, states and `useResource`; moving them to shared folders would touch P1's files.
* Tests: `e2e/incident-model.spec.ts` (rules, no pages) and `e2e/incidents.spec.ts` (flows, access, errors, axe, focus, phone width).

## Gaps and open questions

**For P1 (`common`, admin)**
1. `RolePermissions` gives `INCIDENT_VERIFY_OWN` to employees only, so a technician who reports an incident cannot verify, reopen
   or rate it. Grant it to `TECHNICIAN`; tests pin today's behaviour (flip them then).
2. The admin UI has a `fallbackStrategy`; `AssignmentSettingsView` has no such field, so it cannot be honoured. Add it (additive) or drop the field.
3. The admin UI offers `MANUAL`, `ROUND_ROBIN`, `SKILL_BASED` but not the seeded default `LOAD_BASED`.
4. Admin technician profiles have skill names and one level; the SPI has proficiency 1 to 5 per category (the mock maps junior/intermediate/senior to 2/3/5).
5. Is a non-positive technician `maxWorkload` really "use the default"?

**For the team**
6. `PENDING_INFO` and `REOPEN` are my additions; the spec lists stages, not states. Confirm with P2 and P4.
7. Recommendation weights are placeholders. Is there a formula in the spec?
8. Add a `CANCELLED` state? Auto-close after verification? A retry when a technician frees up after `NO_ELIGIBLE_TECHNICIAN`?
9. Should a low rating require a comment, or feedback expire after N days after closing?

**Not built:** the `TechnicianWorkloadProvider` implementation, the assignment service, REST endpoints, the historical-resolution query (the UI shows it from mock data), and `lastAssignedAt` persistence.
All wait on P2's incidents schema (the endpoints also need incident state and reporter).
